## 一、连接存活、可开新会话与作业存活是三件事

旧 SSH master 进程和 TCP 连接仍在，新增命令却报 `Session open refused by peer`。随后客户端回退到全新认证，出现 `Permission denied`，并不证明原 master 已断开。最初把问题解释成用户需要重新登录不够准确，后来按 socket、进程、TCP 和实际新会话分别核验并纠正。

原 master 上还挂着 CPU 控制链路，关闭它可能连带破坏作业步骤。不能因为新会话被拒，就执行 `ssh -O exit/stop` 或杀 master；也不能把本机 pipe 数、客户端进程数直接等同远端 SSH 会话数、再断言服务端容量已满。服务端为何拒绝旧连接的新通道仍没有确证。

用户配合建立的第二条主连接使用 `cm2`。新命令必须显式指定 `ControlPath=/home/hongzefu/.ssh/cm2-%r@%h:%p`、`ControlMaster=no`、`BatchMode=yes`；裸 `ssh greatlakes` 仍可能走旧配置。计算节点认证失败与登录节点复用是不同问题，已有 cm2 后不继续尝试无授权直连或修改密钥。

**教训：** 描述连接故障要说清是哪一层失败，用实际命令回执确认；原有连接、作业及用户现场不能成为试错清理对象。

## 二、作业 RUNNING 不等于四张 GPU 正在评估

GPU hold 可以正常 RUNNING，却只剩 `batch/extern`，没有模型工作步骤。历史第四张卡曾因一次查询超时没有继续起守卫、没有派分片，形成空占。判断实际使用必须检查精确 worker step、客户端 PID、进度和合法动作或已完成结果，不能只看分配状态或显存。

Slurm 作业与步骤的格式字段也不同。`squeue --steps` 在当时不支持 `%T`，可能 stderr 报错而退出零，stdout 留下字面 `%T`。只检查返回码会漏掉这个失败。步骤清单用已验证的 `%i %j`，真实终态另取精确 `sacct` 的 State、ExitCode、JobName。

**教训：** 资源到位、进程存在、加载通过、实际动作、正常终态、媒体交付逐层取证；正常执行而任务成功位为零仍是有效评估，不能挑成功重跑。

## 三、共享盘偶发读失败不能直接等同进程失联

历史守卫遇到 turbo NFS 的 `Errno 121`，立即退出，进而触发监督器停止；控制器查 GPU 的一次五秒超时也曾使空席无法接续。读失败、查询状态未知、已验证心跳过期，必须分开处理。

有限重试只适用于明确瞬态故障，如 `EIO(5)`、`EREMOTEIO(121)`、`ESTALE(116)`。缓存必须绑定版本、运行、GPU 与守卫身份；重试期限取原已验证 `t/loop_t` 的真实失效时间。不能靠不断重新起计时，把持续未知变成永远健康；错误来源或陈旧内容也不能因磁盘偶发问题被放行。

**教训：** 给查询命令加 timeout 只是第一层。读取、目录扫描、哈希、原子写入及检查器自身也可能阻塞，不能把一个五秒 `squeue` timeout 说成整条监督链已有总期限。

## 四、协议切换前要移存旧控制槽，不能只复制备份

恢复十一的准备程序只保存旧控制槽副本，没有移出活动路径。新监督器和新守卫在第一次新心跳出现前读到旧版本心跳而误退；随后控制器读旧 guardian 心跳拒绝派发。这是本次准备操作的具体错误，不能归责模型或 GPU 失联。

修复时先确认对应 CPU 进程已退出、守卫步骤已结束，再按明确文件路径与 SHA 原字节移存旧心跳、ready、停止意图和启动回执。不能移存仍在运行的控制器心跳，不能清空整个 control，也不能删除真正的新错误来假装恢复。历史首因采用精确路径与 SHA 白名单，改字节、新实例或未知错误仍拒绝。

**教训：** 不可变证据与当前协议槽用途不同。证据永久保存；已退出实例占用的当前槽要在版本转换时退出活动命名空间，否则新版本的 fail-closed 校验会正确拒绝它。

## 五、依赖操作要等真实完成回执，再做下一步

本次一次输入检查启动时 rsync 尚未结束，缺文件守卫立即拒绝。这是主会话没有在工具仍返回 session ID 时等待完成造成的顺序错误。保留失败日志，等 rsync 明确退出零后重新核验，没有因此启动模型。

执行调用已返回、工具等待已结束、后台进程已完成，不能混为一谈。源文件不存在的原因可能是同步未完成，不能马上判断仓库缺文件或绕过检查。后续正式复制只允许新目录，不能用覆盖或删除来取得表面的 clean。

**教训：** 有依赖的工具调用必须逐步检查退出状态；失败与成功日志都保留，不用后一次成功覆盖前一次失败。

## 六、NFS 权限差异与源码字节差异要分开核验

恢复十二两个空席 worker 在模型加载前被 `mme_vla_dirty` 拦截。实际 diff 显示 NFS 把 `100644` 表现为 `100755`；完整二千二百八十五文件的大小和 SHA 与固定源清单一致，没有模型代码改动。

仅在本轮新冻结副本的 Git 元数据中采用旧 NFS 副本已有的 `core.filemode=false`；SimpleMemVLA 的既有 LFS 属性与实际 Git blob 表示不一致时，沿旧副本的 `cat` 过滤配置校验。六个仓库最终状态为空，五个 pin 与每项源码字节保持。没有修改源仓、权重、全局 Git 配置或 `allow_dirty`，更没有改模型代码来绕过预检。

配置顺序也重要：先校正各子仓元数据，再检查父仓，否则父仓会因子仓仍脏而拒绝。最初在子仓校正前检查父仓，失败日志同样保留。

**教训：** 字节清单、Git HEAD、Git clean、真实包导入路径和二进制资产身份各有不同保证。单项通过不能替代其他项，也不能把诊断用忽略权限等同允许源码内容变化。

## 七、零尝试加载失败与已经执行的失败身份不能同样恢复

两个 `mme_vla_dirty` 拒绝发生在加载前：进度 `context_load`、`episodes_done=0`、key 为空；席位账本只有预算头，无报告、attempt、对应身份 reserve 或 reset。完整保留两个 invocation 与两个席位输出目录后，才允许重新进行一次加载。

这与已预约并真实运行后超时完全不同。旧 `VideoUnmaskSwap_xhard1_16501700` 保留原一次 reserve、失败报告和部分 raw，不能重新领取；随后执行的是未尝试的 `16501800`。没有预约的加载重启要单独记次数，不能笼统说所有重试均为零；轨迹重试仍为零。

**教训：** 恢复依据是身份、实际消耗和证据，不是错误看起来是否容易修。保持同一累计预算，不换账本、不换 run_name 来绕额度；不能用“最终交付数”代替全部首试、失败与 reset 的累计消耗。

## 八、外层关闭录像不等于官方循环不编码视频

GroundSG 的原官方循环内部仍会生成临时 MP4，外层 `--no-render` 只关外层视频。用户已决定允许内部临时编码、只交付原始录像；不能为了消除临时文件擅自改第三方 evaluator 或冻结录像器。

官方临时媒体编码可能在环境已经观察到成功后失败。异常分类必须区分模型错误与媒体／记录基础设施错误，并保留真实成功观察、实际步数和首因；不能把 `OSError`、broken pipe、无空间等统一编成模型失败零分。

原始交付也不只是两份视频：需核 AV1 4:4:4 格式、双相机完整解码与时间戳、原始帧指纹关联、动作、状态、数组索引／dtype／shape／哈希、终态和回执。合法缺失状态必须明确声明，不能伪称状态完整；只有本机完整校验与 SHA 回执通过后，才允许删除对应 NFS 大文件，小证据保留。

**教训：** 内部临时产物、官方展示视频、原始交付、任务成功四个概念要分开，不通过模糊“录像关闭”改动执行语义。

## 九、超时退出必须闭合生产者和消费者的同一协议

真实 `os._exit(75)` 不执行 `cmd_run` 的 finally。旧报告是稀疏 infra 行，进度仍为 `episode`；消费者如果一上来要求普通成绩字段或 `finished/75`，会错误退出而无法接续。

新生产器统一出口字段。外壳只有在真实 wait 得到七十五后，核原客户端 PID、JobID、StepID，再补有限写入的终态。旧稀疏协议只有锁定源码 `33bef4f…` 与配置 `6eb5cd…`，加真实 `FAILED/75:0`、原 dispatch、身份清单、报告原行、预算和领取闭合才兼容；不改旧进度、不把任意 episode 当成合法失败。

完整失败证据独立保存，未知 `task_success/exec_steps` 维持 null。错误报告不是正常录像发布；没有媒体不能编一个合格回执。

**教训：** 消费者手写 `finished75` 的夹具不能证明生产者真的会写它。必须串真实看门狗子进程、真实 shell wait、实际 JSON、结算及消费者校验。

## 十、超时线程和主线程之间也有结算竞态

先发布 `fired`、后构造 `timeout_result` 会让主线程读到不存在的结果。即使结果已存在，写入阻塞时主线程仍可能普通 `_end` 清空身份、甚至领取下一局，之后计时线程才硬退出，误结算或丢协议。

修复原子发布触发与结果，等待退出钩子完成；未完成则明确阻塞退出，不允许普通结算或下一领取。生产硬退出有限等待全部文件、锁与账本操作，写日志或诊断失败也不能让进程无限存活。

**教训：** 锁只保护局部变量不够，要检查整个生命周期的所有权：何时允许返回、何时清 current、何时允许新 claim。用真实事件阻塞结果写入并放行模型返回来构造反例。

## 十一、成功字段、状态和基础设施结果必须独立

普通 `success/fail/timeout/error` 与环境实际观察的成功零／一不是同一个字段。模型异常或执行步数期限发生时，已观察到的一仍应保留；未观察不能默填零。正常任务失败不重试，缺少必要成功观察或协议损坏作为基础设施异常单独留证。

步数期限必须在进入超额真实 `env.step` 前拒绝，不把被阻止的动作写成实际执行。完整客户端耗时包括请求准备、子目标、传输、响应解码和动作返回；server-only 时长、recv 时间戳、合成历史指标不能冒充完整决策时长。

**教训：** 既要防“异常一律零分”，也要防“某回合有成功信号就把全部执行和媒体都判成功”。数值、结构、行为和交付一致性应分别说明。

## 十二、幂等恢复要覆盖每一个写入边界

本地 attempt_end、共享预算 commit、queue 收尾、正常 accept、报告追加与最终 settlement_complete 之间任一点退出，都可能留下部分完成。恢复按原 attempt_id／rid 补未完成步骤，不能新 reserve、重复扣 reset、重复发布、漏写报告或改变原 infra 状态。

身份错误采用原预约退回与 void，不误按正常执行消耗。真实超时 result 已落盘、账本锁阻塞导致 attempt_end 未写时，恢复还必须保留合法 `exit_kind/exit_code`；此前 `_result_row` 丢两字段，使已证超时被再次判成未经许可 infra，后来补齐并串真实子进程恢复测试。

**教训：** 独立的“写边界测试通过”和“忙锁硬退出通过”不等于两条链相接。边界矩阵还要分别覆盖正常结果、合法超时、身份 void 和非法数据；字段比较类型严格，不能让 bool、float 与整数自动相等掩盖冲突。

## 十三、进程退出与终态文件可见性存在真实时间差

零／六／七十五退出之后，报告、进度、预算和 `sacct` 未必同时可见；PID 消失不自动意味着成功或可重新派发。有限确认窗口要把部分 JSONL、缺文件、延迟记账和最终完整性分开处理，同时让其他健康席位继续。

逻辑 shard、运行 segment 和续段号必须独立。恢复 `resume-1` 后再遇七十五，要生成 `resume-2`，再次接管仍识别原 segment；不能重置编号碰撞目录，不能重跑已 reserve 身份。

**教训：** 未闭合状态保留为未知并留证，不能回退成新首试。只有证据闭合才能宣称已结算；正常退出码也不替代完整报告。

## 十四、暂停、附着、完整与不完整必须共享严格契约

有基础设施失败时，暂停应满足 `accepted + infra = settled`、`settled + remaining = expected`，不能有的组件用 published、有的用 settled。指针须锁定证明 SHA，显式零字段不能缺失。

历史暂停恢复允许按已锁预算前缀复用证据，但推断当前控制器已暂停不能只看旧前缀。附着监督看不到 Popen 的原退出码，所以还必须绑定当前上下文、PID、启动时间、活 STOP、证明路径、当前完整预算长度和 SHA，拒绝旧证明及新增预约。

搬运收到 STOP 后只核已有回执、记录严格 PAUSED 并退出六，监督继续等控制器排空；不能把 STOP 一律写成搬运故障，也不能在刚看到 STOP 时先退出监督。直接、附着和 shell 守卫都应消费实际生产的同一 JSON。

最终四千身份要由正常发布、独立失败、未闭合和未尝试集合互斥覆盖。基础设施失败一，即使其余三千九百九十九全部交付，也只能 INCOMPLETE；“所需正常媒体都搬完”不能替代“原四千份合格交付完整”。

**教训：** Counter 序列化可能丢零，`.get(key,0)` 会把未知伪装成成功。验收要真正写 JSON 后读回，完整、不完整、暂停及附着四条消费路径都要覆盖。

## 十五、心跳时间、真实进展和阶段期限不能混用

新 Seat 保留真实进展起点 `t/t_progress`，独立线程更新 `t_heartbeat`。旧 33 生产器只有 `t` 心跳。控制器接管和运行两处误读现代 `t`，造成加载已持续一百九十七秒、实际心跳仍新鲜却被判失联。

最后修复严格优先显式 `t_heartbeat`；现代缺项、非有限值、非法类型、未来或陈旧都拒绝，不能回退到 `t`。只有锁定旧来源允许旧 t-only 格式。真实进展、失联一百二十秒和加载三千六百秒的期限保持独立，不为了通过放宽阈值。

**教训：** heartbeat-only touch 不能掩盖主任务静默空转；反过来，真实进展未改变也不代表常驻加载进程失联。跨版本协议应有明确来源和完整序列化夹具，不能只分别审生产与消费。

## 十六、短稳定窗口和大量单测不能证明长期监督健康

三路最终对抗复核锚定 891，五百独立 CPU 用例通过；最后心跳修复锚定 75b722f，一百六十七控制核心及主十一用例通过。CPU 夹具确实串了真实看门狗、文件、外壳和消费者，但模型、环境和 Slurm 状态有替身，完整交付部分输入为合成报告，不能说所有实际 GL 异常都已验证。

恢复十四二百二十四秒窗口四 worker、监督、控制和守卫均健康；后续持续监控又暴露监督主循环超过一百二十秒未推进。`loop_t=1791732434.359236`，独立线程还写到 `t=1791732557.6545706`，差一百二十三点二九五秒。守卫正确按 loop 超时拒绝，四守卫退出八；监督器收到异常后退出一，GPU 和 CPU hold 没有被取消。

这证明监督主循环无进展、独立心跳线程仍活。不能据此断言具体阻塞在 NFS 或 squeue：监督进程已死，代码未留当时循环阶段或堆栈，无法追溯。文件 exists/glob/read/stat/hash/atomic 等无统一执行期限是候选风险；Slurm 查询已有五秒 timeout，四守卫已登记时相关函数主要只重写启动记录。

**教训：** 所有“稳定”“通过”须带锚点、环境与时间窗；后续新证据要覆盖旧结论的适用范围。没有栈和阶段日志时，诚实写未知，不把合理猜测写成根因。

## 十七、后台存活、阶段接续、通知和代理唤醒分别验收

detached tmux 保证进程脱离代理会话，不保证下一阶段会启动，更不保证代理自动醒来。程序通知 sendmail 返回零只说明提交；只有最初探针由用户确认实收。既有相同收件人／通道证明可按已批准范围复用，但不能把每封新失败邮件写成已收到。

监督器停止后，控制器可被 PID 一接管继续评估，搬运也可继续；这符合异常只停监督器的口径，却不意味着正式监督已经恢复。观察器退出、监督器退出、控制器退出、GPU 作业回收是不同事件，必须逐项说清。

**教训：** 没有受支持的自动唤醒成功回执，不能承诺代理无人值守修复未来故障。监控脚本结束时也只回收它自己创建的只读 tail，不能退出整套评估。

## 十八、子代理与审查需要清晰职责和次数边界

代码修复用独立工作树，单文件单 owner；运行代理只执行固定版本、命令和资源，不在发现问题后自行改代码、参数或依赖。固定 BASE/TIP 静态审查只看当时快照；真正执行 CPU 生产器验证另由运行职责完成，主会话负责整合、预算、资源与证据。

只给子代理一句“审所有异常”不够，需明确状态矩阵和 producer→序列化→consumer 链。发现实质反例修复，措辞不无限打磨。用户设定最多五次审查、最后最多第六次修复后直接运行，应明确最后修复的测试证据和未再全面复审的边界，不能无限期循环。

**教训：** 测试数量、某代理 PASS、分段通过不能替代完整接口审查；也不能把分工当扩大授权、预算或修改受保护源码的许可。

## 十九、监控计数要有不变基线和正确分母

“每 GPU 再四局”以本次固定 baseline 的 rid 集合为准，不使用全轮累计已完成数，也不把原来各完成三局直接补算成新目标。只计正常预算 commit 且有 matching publication、搬运回执和独立成绩零／一的身份；不计 reserve、活进程、部分媒体或基础设施失败。

首次只读观察器同时要求监督与控制心跳健康，因此在监督停止而控制健康时退出。恢复观察时保留原 baseline、已计数身份和原错误日志，不重新从零计算；单独告知监督故障，继续只读看实际交付，没有改评估、补跑或重启模型。

较快 GPU 达到四局后仍可继续原评估，不能为使统计正好等于四而停它。整体监控结束条件是四片都至少四；用户中途暂停优先于该目标，必须记录未完成范围。

**教训：** 执行完成数、成功数、已尝试数、已搬运数和任务类型数要分别表达，恢复监控也不能换分母。

## 二十、保留证据并精确收尾，不能为了 clean 破坏现场

冻结 worker、CPU 编排、配置与来源 manifest 各自固定 SHA。更新 CPU 消费者时不热改已运行的四个模型快照；已完成首局、结果和预算身份复用，不为重走流程重跑。

历史错误只按路径／SHA认可，新错误写唯一文件，不覆写首因。暂停与失败目录原字节移存，源码内容、参数、预算、恢复路径和执行模式的改变分别记录。只提交本轮明确文档／代码，提交立即推送 dev，不公开同步 main，不触碰他人在途修改。

只允许按登记的确切会话删除，删前删后各查一次；禁止 kill-server、全用户 scancel、批量前缀清理、关闭旧 SSH master、全局 GPU 查询忙循环，以及清空 artifacts／穿透资产 symlink。本次没有修改冻结 benchmark 录像器或受保护源码。

**教训：** 可恢复性依赖原日志、版本、身份、预算、产物与错误链一起保留。主会话应承担自己的依赖顺序和协议槽准备错误，不把基础设施、模型、工具等待或用户授权当作模糊解释。
